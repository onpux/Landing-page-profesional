Engineering Showcase

A production-grade static web application built exclusively with HTML5 and CSS3. Zero frameworks. Zero build step. Open index.html and go. Read the Engineering Contract →

Objective

This project verifiably demonstrates mastery of the competencies evaluated by the freeCodeCamp Legacy Responsive Web Design v8 Certification through clean, accessible, and professionally organized code.

Every element exists to solve a concrete problem. Nothing was added to "show off" knowledge. Competencies are evidenced as a consequence of solving real layout, accessibility, and responsiveness challenges.

Project Constraints

These constraints define the boundaries within which every decision is made. They are not negotiable.

Zero Dependencies
No Bootstrap, Tailwind, Bulma, Foundation, Sass, Less, PostCSS, jQuery, React, Vue, Angular, icon libraries, Google Fonts, or any external dependency. The project must work by opening index.html.
Zero JavaScript
Only HTML5 and CSS3. No JavaScript files, no inline scripts, no event handlers. Any UI behaviour that can be solved with HTML/CSS must use HTML/CSS.
No Build Step
Open index.html directly in a browser. No bundlers, transpilers, watchers, or preprocessors.
Mobile First
Base styles target the smallest viewport. Desktop adds capability via min-width breakpoints.
WCAG 2.2 Level AA
Accessibility is a requirement from the first line of code, not a layer added after.
Semantic HTML
Document structure must be meaningful without CSS. No <div> where a semantic element is appropriate.
System Font Stack
Zero HTTP requests for typography. Better performance, privacy, and offline availability.

How to Review

Estimated time: 15–20 minutes

  1. Read the Project Constraints — understand the deliberate limitations.
  2. Open DevTools → inspect :root — verify CSS custom properties (design tokens).
  3. Resize viewport from 320px through 3840px — verify responsive behaviour.
  4. Keyboard navigation — Tab, Shift+Tab, Enter, Space — verify skip link and focus rings.
  5. Inspect semantic HTML — verify header, nav, main, section, article, figure, aside, footer.
  6. Review the Engineering Decisions — each decision shows the problem, alternatives, implementation, and verification.

Engineering Decisions

Each decision documents the problem, the alternatives considered, the chosen implementation, and how it was verified. These are not post-hoc rationalisations — they were recorded during development as decisions were made.

Why CSS custom properties over a preprocessor? Decided

Problem: The project needed runtime theming (light/dark) without JavaScript.

Alternatives: Sass variables (compile-time only), PostCSS (build step required), CSS custom properties (runtime native).

Decision: CSS custom properties. They enable prefers-color-scheme theming without JavaScript or a build step.

Trade-off: Cannot use custom properties inside @media query conditions, but can use them in values.

Verification: Inspect :root in DevTools — tokens change when toggling system theme.

Why <details> over a JavaScript accordion? Decided

Problem: Engineering decisions needed expand/collapse behaviour without bloating the page.

Alternatives: JS with click handlers (breaks zero-JS constraint), CSS :target (fragile with navigation), <details>/<summary> (native HTML, accessible).

Decision: <details>/<summary>. Keyboard accessible, screen-reader friendly, zero JavaScript.

Trade-off: Limited animation control. The open/close is instant. But prefers-reduced-motion is automatically respected.

Verification: Tab to any decision, press Enter or Space — expands without JavaScript.

Why system font stack over Google Fonts? Decided

Problem: Zero external HTTP requests was a hard constraint, but typography needed to be readable and professional.

Alternatives: Google Fonts (R05 violation), @font-face with local files (file size), system font stack (zero requests).

Decision: System font stack. Zero HTTP requests, faster load, better privacy, works offline.

Trade-off: Less typographic control across OSes, but the fallback chain ensures consistent readability.

Verification: Open DevTools → Network tab — zero font requests. Font renders differently on each OS (expected).

Why Mobile First with min-width queries? Decided

Problem: The responsive strategy needed to serve the majority of users efficiently without overcomplicating the CSS.

Alternatives: Desktop First with max-width (optimises for desktop, overweight mobile CSS), Mobile First with min-width (base=mobile, smaller CSS).

Decision: Mobile First. Base styles assume the smallest viewport. Media queries add capability for larger screens.

Trade-off: Requires more forethought for desktop layouts, but results in smaller CSS and better mobile performance.

Verification: Resize browser from 320px to 3840px — layout adapts at 640px, 1024px, 1440px.

Why BEM naming over utility classes? Decided

Problem: CSS class naming needed to be self-documenting and maintainable without a preprocessor.

Alternatives: Utility classes (Tailwind-like, verbose HTML), SMACSS (requires mental categories), BEM (self-documenting).

Decision: BEM (.block__element--modifier). Most widely adopted convention in production CSS. Reads like documentation.

Trade-off: More verbose class names. But no preprocessor means what you see is what you get.

Verification: Read any CSS file — .card, .card__title, .card__demo. Hierarchy is obvious from the names.

Why Semantic HTML over <div>-based structure? Decided

Problem: The page structure needed to be accessible without CSS, and the project needed to demonstrate semantic HTML competency.

Alternatives: <div> for everything (works, no semantics), semantic elements (built-in accessibility, meaningful structure).

Decision: Semantic HTML. Every <section>, <article>, <nav>, and <aside> conveys meaning without CSS.

Trade-off: Some semantic elements need explicit reset styles (default margins, display values).

Verification: Disable CSS in DevTools — the document structure is readable and navigable.

Architecture

The project follows a layered CSS architecture, semantic HTML structure, and a component discovery process that lets the implementation reveal the design.

Why this architecture?

The cascade is the most powerful feature of CSS. Fighting it with specificity wars is a sign of poor architecture. By organising layers from lowest to highest specificity, any rule can be overridden predictably. Components are isolated. Theme changes affect only colour tokens. No rule breaks another.
